# Primary-source hardening delta — 2026-09-25

**Scope:** fresh, implementation-focused research on skill admission/provenance, issue-backed write-ahead records (WAL) and review evidence, privacy/legal risk framing, and CI/software-supply-chain controls. This supplements—not replaces—the broader [2026-08-25 baseline](./agentic-repository-baselines.md).

**Research/access date:** 2026-09-25 UTC. Sources were limited to official specifications, standards, legal texts, regulator guidance, first-party product documentation/specifications, and project-owned source documentation. No package or third-party skill was installed or executed; no GitHub state was changed.

**Repository snapshot:** local `AGENT_TEMPLATE` at HEAD `9b49ba2bed981fa3bff16a7d9d5d5750c1d05183`, plus uncommitted work present at inspection time. Current-state statements below are observations, not assertions about the remote default branch. Re-check them before implementation.

## Bottom line

The template already has good intent: full-SHA action pins, read-only checkout credentials, Dependabot, a strict issue shape, privacy disclaimers, typed evidence, and an in-flight whole-tree skill digest. The highest-value hardening is to finish and test that skill binding, preserve each material change’s pre-change acceptance contract in reviewable Git history, and stop giving untrusted repository code a general-purpose GitHub token. Add credential-free PR scanning and protected-branch enforcement next; make provenance/SBOM workflows opt-in when a real release surface exists.

## 1. Skills: validate format; separately prove admission and content

**Source facts.** The Agent Skills format permits `SKILL.md`, scripts, references, assets, and arbitrary additional files. Its complete frontmatter list has no signature, content digest, or publisher-verification field; `metadata` is client-defined and `allowed-tools` is explicitly experimental ([Agent Skills specification](https://agentskills.io/specification)). The official client guide warns that a project-level skill comes from a repository that may be untrusted and recommends trust-gating its loading so the repository cannot silently inject instructions ([Agent Skills client guide, “Trust considerations”](https://agentskills.io/client-implementation/adding-skills-support#trust-considerations)). A skill’s metadata cannot replace host enforcement: Anthropic states that prompt/permission instructions shape what an agent attempts but do not change what the host allows ([Claude Code permissions](https://code.claude.com/docs/en/permissions)). For immutable references, GitHub calls a full commit SHA the only immutable action reference; **[inference]** that establishes reproducibility of the referenced object, not by itself the publisher’s identity or authorization ([GitHub Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use)).

**Observed state.** The uncommitted checker now requires a 40-hex commit or SHA-256 `revision` plus a `content_digest`, computes a deterministic digest over every file in each third-party skill directory, and rejects a mismatch ([`tools/repoctl.py:276–397`](../../tools/repoctl.py#L276-L397)). That closes the main “ledger says one thing, vendored bytes say another” gap. The digest covers sorted relative paths plus file lengths/data but not executable mode, and the current manifest has no live third-party entry to exercise the path ([`project.toml:56–64`](../../project.toml#L56-L64)); the check also does not run the Agent Skills format validator.

**Template recommendations.**

1. Trust-gate repository-provided skills before discovery/activation, and keep host permissions, sandboxing, network policy, and secret isolation outside the skill package.
2. Finish and test the in-flight content binding. Retain canonical source, full commit, exact subdirectory, whole-tree digest, licence, scripts/dependencies, requested and observed file/network/process effects, reviewer/date, and rollback. Include file mode in the digest if executable bits matter, and treat commit identity/signature verification separately from local content binding.
3. Add an offline CI check that rejects changed, missing, or extra third-party skill files and runs a pinned format validator where available. The standard’s `skills-ref` validator checks frontmatter/naming, not malicious behaviour ([Agent Skills specification, “Validation”](https://agentskills.io/specification#validation)).
4. Review updates as code diffs, including instructions and permission changes; never silently replace an admitted privileged skill. This is a template supply-chain decision, not a requirement imposed by the Agent Skills format.

## 2. Issue-backed WAL and review evidence: useful coordination, not an immutable log

**Source facts.** GitHub Issues are intended to plan, discuss, and track work, and a pull request can be linked to its issue ([GitHub Issues](https://docs.github.com/en/issues/tracking-your-work-with-issues/learning-about-issues/about-issues); [linking a PR to an issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)). Issue titles and descriptions remain editable, and the description edit history can be removed by the author or a writer ([GitHub, “Editing an issue”](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/editing-an-issue)). Protected branches can require pull-request review, status checks, resolved conversations, dismissal of stale approvals, and no bypass; these are repository settings, not facts proven by a workflow file ([GitHub protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)). Active vulnerabilities can remain in a private repository security advisory and be published after remediation ([GitHub repository security advisories](https://docs.github.com/en/code-security/concepts/vulnerability-reporting-and-management/repository-security-advisories)).

**Observed gap.** The ADR deliberately avoids an append-only agent event log ([ADR 0001](../adr/0001-issue-backed-write-ahead.md)). The PR workflow now requires an open issue, a closing keyword, and the profile's canonical contract, but it still does not prove that the acceptance contract existed before the first code-changing commit or that the issue body was immutable ([`require-issue-reference.yml`](../../.github/workflows/require-issue-reference.yml)). The issue template’s evidence taxonomy is good, but the PR/reference gate does not bind completion evidence to an exact head SHA.

**Template recommendations.**

1. Keep the issue as the live work register, but add one small, redacted **pre-change receipt commit** for behavior, schema, security, privacy, legal, or operational work. It should contain the issue URL/number and creation time, canonicalized acceptance-contract SHA-256, scope/non-goals, risk/disclosure class, verification plan, and receipt commit; exclude secrets, exploit details, and personal data. Require this commit to precede implementation commits. This preserves intent without creating an agent-event ledger.
2. Link the PR natively and record base/head SHAs, focused/aggregate check URLs, independent review decision, artifact digests, and typed evidence. Require the issue-reference and repository-contract checks, a latest-head approval, resolved conversations, and disabled bypass on protected branches. Do not treat a mutable issue, green CI, or another model’s confidence as completion by itself.
3. Keep active vulnerabilities in the private advisory route. The untrusted public PR workflow must not query or claim verification of a private advisory; a maintainer may record a redacted GHSA/private-advisory reference after disclosure is authorized through a trusted review path.

## 3. Privacy/legal framing: collect facts and evidence, never self-certify compliance

**Source facts and boundaries.** GDPR scope is fact-dependent: Article 3 addresses processing in an EU establishment and, for a non-EU establishment, offering goods/services to people in the Union or monitoring behaviour ([GDPR Article 3](https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng#art_3)). Article 5 requires lawfulness/fairness/transparency, purpose limitation, minimization, storage limitation, integrity/confidentiality, and accountability; Article 5(2) places responsibility for demonstrating compliance on the controller ([GDPR Article 5](https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng#art_5)). Therefore **[inference]** a generated repository checklist cannot establish compliance. Article 25 requires data-protection measures in design and by default ([GDPR Article 25](https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng#art_25)); the EDPB says this should be considered before processing and reviewed during the lifecycle ([EDPB Guidelines 4/2019 v2.0](https://www.edpb.europa.eu/documents/guideline/guidelines-42019-on-article-25-data-protection-by-design-and-by-default_en)). Article 30 specifies processing records subject to limited exemptions ([GDPR Article 30](https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng#art_30)); Article 32 makes security measures risk-appropriate ([GDPR Article 32](https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng#art_32)); and Article 35 requires a DPIA for processing likely to result in high risk ([GDPR Article 35](https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng#art_35)). These are EU requirements, not a global legal checklist.

**Template recommendations.**

1. Expand the factual data inventory to include prompts/transcripts, issue bodies, review artifacts, CI logs/artifacts, support exports, agent memory, and skill contents as possible data stores—not only product databases ([data inventory](../legal/data-inventory.md)).
2. Use non-conclusive states such as `scope-unknown`, `role-pending-counsel`, `lawful-basis-pending`, `dpia-screen-pending`, `technical-control-observed`, `production-evidence-attached`, and `counsel-reviewed`. Reserve “compliant/conforms” for a project-specific qualified assessment.
3. Trigger renewed review when a new field, purpose, recipient, region, retention period, minor-facing flow, model/tool/provider, automated decision, or agent permission changes. A DPIA screening answer is not itself a DPIA, and an engineering inventory is not automatically the organization’s formal record.
4. Keep the existing public-safe/private disclosure split and counsel gate. A repository template can reduce risk and assemble evidence; it cannot select jurisdiction, roles, lawful bases, special-category handling, transfer mechanisms, or legal conclusions.

## 4. CI and software supply chain: isolate trust, then add provenance when publishing

**Source facts.** GitHub recommends full-SHA action pins, least-privilege `GITHUB_TOKEN`, auditing actions, separating untrusted checkout from privileged context, avoiding `pull_request_target` with untrusted code, and code-owner review for workflow changes ([GitHub Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use)). That same page notes that Dependabot alerts do not cover actions pinned only to SHA values, so pin immutability needs a complementary update/review process. Workflow and job permissions can be scoped separately ([GitHub workflow syntax, `permissions`](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)). OIDC can exchange workflow identity for a cloud token valid only for one job, with the cloud trust policy constraining repository/ref/other claims ([GitHub OIDC](https://docs.github.com/en/actions/concepts/security/openid-connect)). For real releases, GitHub can bind an artifact digest to signed in-toto/SLSA provenance and SBOM attestations ([GitHub artifact attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations)); SLSA v1.2 requires progressively stronger authenticity and build isolation, so producing an attestation alone is not a higher-level claim ([SLSA v1.2 build requirements](https://slsa.dev/spec/v1.2/build-requirements)). Dependency review should gate newly introduced vulnerable dependencies when an ecosystem/lockfile exists ([GitHub dependency review](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependency-review)). `zizmor` is a primary-project static analyser for CI/CD patterns including template injection, credential leakage, excessive permissions, and unsafe Git references ([zizmor project](https://github.com/zizmorcore/zizmor)). OpenSSF Scorecard is useful heuristic evidence, but its own documentation says checks have false positives/negatives and an aggregate score is not definitive or one-size-fits-all ([OpenSSF Scorecard](https://github.com/ossf/scorecard)).

**Observed strengths/gaps.** The workflows already use full-SHA checkout/scanner actions, `persist-credentials: false`, read-only top-level permissions, and hosted runners ([`ci.yml:7–27`](../../.github/workflows/ci.yml#L7-L27), [`specialist-scans.yml:15–48`](../../.github/workflows/specialist-scans.yml#L15-L48)). However, `ci.yml` explicitly exports `GH_TOKEN` into `make verify`, which invokes declared surface commands ([`Makefile:43–49`](../../Makefile#L43-L49), [`tools/repoctl.py:981–1024`](../../tools/repoctl.py#L981-L1024)); the issue-reference job requests `security-events: read` without using it ([`require-issue-reference.yml:6–10`](../../.github/workflows/require-issue-reference.yml#L6-L10)); and specialist scans run only on trusted pushes/manual dispatch. Repository settings are documented as an external assumption, not an enforceable local control ([threat model assumptions](../../.security/threat-model.md#7-assumptions-and-accepted-risks)).

**Template recommendations.**

1. Remove `GH_TOKEN` from general verification. Set top-level `permissions: {}` and grant only the scopes each job needs. Keep write tokens in dedicated issue/release jobs that do not execute untrusted project code; remove unused `security-events: read` now.
2. Add a credential-free hosted-runner PR workflow for `zizmor` and, when applicable, dependency review. Keep licensed Gitleaks on trusted pushes if fork secrets are unavailable, and add provider secret scanning/push protection where available. Pin every added action to a full SHA and periodically review pinned updates manually because SHA pinning can hide Dependabot alerts.
3. Require protected-branch PRs, latest-head review, required checks/conversation resolution, no bypass, and code-owner review for `.github/workflows/**`, `.agents/skills/**`, `project.toml`, security/legal records, and provenance locks. Run Scorecard periodically and triage named checks; do not turn its aggregate score into sole approval.
4. Add release provenance, SBOM, OIDC deployment, dependency review, and [GitHub immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases) only when a product/release surface exists. Pin the attestation action, publish by digest, verify attestations in a separate trust path, and make no SLSA-level claim without assessing the actual producer and builder.

## Limitations

- This was documentation/source research, not a penetration test, CI execution, package audit, legal opinion, DPIA, or control certification.
- GitHub feature availability varies by plan, repository visibility, and event type; settings must be verified on the adopting repository.
- SLSA, Scorecard, and Agent Skills describe different assurance layers; none is a blanket compliance badge.
- Canonical EUR-Lex pages returned an empty HTTP 202 to automated text extraction in this environment. Legal claims above cite the official legal text and were cross-checked against official EDPB guidance and the [European Commission’s GDPR application page](https://commission.europa.eu/law/law-topic/data-protection/information-business-and-organisations/application-gdpr_en); qualified counsel must validate applicability to a real operator.
- Vendor and standards documentation is living material. Recheck versions, supported plans, event semantics, and legal text at implementation and release time.
