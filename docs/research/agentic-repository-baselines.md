# Agentic repository baselines: primary-source research

**Research cutoff and access date:** 2026-08-25
**Scope:** portable, agent-first GitHub repository templates; agent instructions; secure delivery; product quality; privacy and launch readiness; Agent Skills discovery and vetting.
**Method:** first-party specifications, standards, regulator guidance, official product documentation, and first-party engineering reports. Recommendations that are not direct source claims are labelled **[Inference]** or **[Template decision]**.

> **Important boundary:** this is a technical starter baseline, not legal advice, a certification, or a claim that a generated project is GDPR-, WCAG-, SSDF-, SLSA-, or OWASP-compliant. Agent instructions and skill metadata are context, not a security boundary. File, network, identity, secret, and tool permissions must be enforced by the host or CI platform.

## Executive baseline

1. Keep the root `AGENTS.md` a short map: purpose, repository map, canonical setup/check commands, source-of-truth hierarchy, scoped-document pointers, and completion evidence. Put detail in one-hop, owned documents; use nested instructions only for genuinely local rules.
2. Give every durable fact one owner. Treat schemas, executable configuration, and CI as authoritative where possible; generate documentation or client-specific instruction files from that owner and reject conflicting copies mechanically.
3. Make verification runnable and observable. An agent needs the exact build/lint/test commands plus the expected state transition, rendered output, or API/database result that demonstrates success.
4. Harden delivery by default: immutable action/dependency references, least-privilege workflow tokens, short-lived credentials, secret scanning/push protection, protected branches, required review/status checks, SBOM/dependency updates, and release provenance. Never advertise a SLSA level without meeting and verifying its requirements.
5. Give coding agents isolated, short-lived identities and workspaces. No production credentials by default, deny sensitive paths, restrict egress, require approval for high-impact actions, and keep merge/deploy authority with reviewed humans and protected environments.
6. Build modularly from explicit interfaces and measurable quality criteria; do not start by scattering microservices. Test critical behaviour, emit vendor-neutral telemetry without personal data, target WCAG 2.2 AA by default, and keep a navigable documentation index.
7. If the project processes personal data or stores/accesses terminal data, add data inventory, privacy-by-design review, purpose-bound retention/deletion, rights handling, and a DPIA screening step. Cookie UI and national ePrivacy rules require jurisdiction-specific review.
8. Treat skills as code-like supply-chain inputs. Read every file before installation, identify publisher and provenance, derive requested permissions, test in a disposable environment, pin an immutable revision, and review every update. Directory listings and install counts are discovery signals, not trust.

## 1. Agent instructions and repository organisation

### What the primary sources actually say

- **OpenAI/Codex:** Codex reads `AGENTS.md` before work. Project instructions are assembled from the project root to the current working directory, at most one instruction file per directory, with the 32 KiB default cap; closer files appear later and override earlier guidance ([OpenAI, “How Codex discovers guidance”](https://learn.chatgpt.com/docs/agent-configuration/agents-md#how-codex-discovers-guidance)). This supports a concise root file plus genuinely scoped nested files, not a large universal manual.
- **OpenAI’s agent-first engineering report:** OpenAI reports that a “map, not a 1,000-page instruction manual” worked better than a monolithic `AGENTS.md`. Its repository treats a structured `docs/` tree as the system of record, uses a roughly 100-line `AGENTS.md` as a table of contents, and uses linters/CI to check structure, links, freshness, dependency directions, and other invariants ([OpenAI, “Harness engineering”, sections “Agent legibility is the goal” and “Documentation is a tool, not documentation”](https://openai.com/index/harness-engineering/)). This is first-party experience, not a normative standard.
- **Anthropic/Claude Code:** project instructions above the working directory load at launch, subdirectory instructions load on demand, and large projects can use path-scoped rules. Anthropic recommends targeting fewer than 200 lines per `CLAUDE.md`; it warns that long files consume context and reduce adherence, and that contradictory rules may be followed arbitrarily ([Anthropic, “How Claude remembers your project”](https://code.claude.com/docs/en/memory#write-effective-instructions)). The same page distinguishes context instructions from enforced configuration.
- **GitHub Copilot:** GitHub distinguishes repository-wide `.github/copilot-instructions.md`, path-specific `.github/instructions/**/*.instructions.md`, and agent instructions such as `AGENTS.md`. Its precedence list places personal instructions first, then path-specific repository instructions, repository-wide instructions, and agent instructions; it explicitly advises avoiding conflicting instruction sets ([GitHub, “About customizing GitHub Copilot responses”](https://docs.github.com/en/copilot/concepts/prompting/response-customization#about-repository-custom-instructions)). Support differs by Copilot feature, so GitHub’s formats should be adapters, not competing sources of truth.
- **AGENTS.md open format:** the format’s site calls `AGENTS.md` a predictable “README for agents,” recommends a root file, and recommends nested files in monorepos; the closest file to the edited file wins ([AGENTS.md, home and FAQ](https://agents.md/)). It intentionally leaves the file plain Markdown rather than defining a large required schema.
- **Verification:** Anthropic’s primary guidance says to give the agent a check that returns a pass/fail signal—tests, a build exit code, a linter, a fixture diff, or a browser screenshot—and then iterate until it passes ([Anthropic, “Give Claude a way to verify its work”](https://code.claude.com/docs/en/best-practices#give-claude-a-way-to-verify-its-work)). OpenAI reports making the app, logs, metrics, traces, and per-worktree runtime directly accessible so the agent can reproduce bugs and validate fixes ([OpenAI, “Harness engineering”](https://openai.com/index/harness-engineering/)).
- **Human-facing repository entry points:** GitHub says a README should contain only what is necessary to get developers started using and contributing; it also recommends repository health/security files including contribution guidance, a code of conduct, a license, and `SECURITY.md` ([GitHub, “Best practices for repositories”](https://docs.github.com/en/repositories/creating-and-managing-repositories/best-practices-for-repositories), [“Setting up your project for healthy contributions”](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/)).

### Reliable repository pattern

| Concern | Reusable baseline | Evidence status |
|---|---|---|

| Progressive disclosure | Keep always-on context small; move procedures into skills and detailed rationale/reference into one-hop documents. | Client interoperability | `AGENTS.md` is canonical. | Verification | Every instruction names exact commands and expected observable evidence. Required CI checks mirror them. For UI/data changes, verify the running system, not only compilation or a mocked unit test. | Strongly supported by Anthropic, OpenAI, NIST SSDF, and ISO quality guidance. |
| Enforcement | Put security and architecture invariants in schemas, linters, dependency rules, tests, protected branches, and sandbox policy. `AGENTS.md` explains them but cannot enforce them. | **Template decision**, directly supported by Anthropic’s instructions-vs-enforcement distinction and OpenAI’s mechanical enforcement report. |

## 2. Secure, maintainable delivery

### Normative and industry baselines

- **NIST SSDF version status:** SP 800-218 v1.1 is the final voluntary framework and organizes practices around Protect, Produce, Release, and Respond, including protection of code/releases, well-secured software, vulnerability handling, testing, and retained evidence ([NIST SP 800-218 final](https://csrc.nist.gov/pubs/sp/800/218/final), [DOI](https://doi.org/10.6028/NIST.SP.800-218)). NIST’s December 2025 SSDF 1.2 revision is still an **initial public draft** as of this cutoff, not a replacement standard ([NIST SP 800-218 Rev. 1 IPD](https://csrc.nist.gov/pubs/sp/800/218/r1/ipd)). A template may map controls to SSDF, but should not say “SSDF compliant” without an assessment.
- **SLSA current version:** SLSA v1.2 is the approved current specification. Build L1 requires provenance; L2 adds authentic signed provenance from a hosted builder; L3 requires a hardened, isolated builder. The new Source track ranges from version control (L1), through history/provenance and continuous controls, to two-party review (L4) ([SLSA v1.2 specification](https://slsa.dev/spec/v1.2/), [Build requirements](https://slsa.dev/spec/v1.2/build-requirements), [Source requirements](https://slsa.dev/spec/v1.2/source-requirements)). A generic template should generate provenance and protect release refs, then assess the actual builder before claiming any level.
- **GitHub hardening:** GitHub calls a full-length action commit SHA the only immutable action reference, recommends least-privilege `GITHUB_TOKEN`, warns that repository write access can expose workflow secrets, and documents dangerous privileged triggers and shared self-hosted-runner exposure ([GitHub, “Secure use reference”](https://docs.github.com/en/actions/reference/security/secure-use)). GitHub’s security catalogue provides a dependency graph, SPDX-compatible SBOM export, Dependabot alerts/security updates, and secret push protection ([GitHub, “GitHub security features”](https://docs.github.com/en/code-security/getting-started/github-security-features)).
- **Short-lived CI identity:** GitHub OIDC lets a workflow exchange its identity for a cloud token valid only for the job; the cloud trust policy must bind claims so untrusted repositories cannot obtain the role ([GitHub, “OpenID Connect”](https://docs.github.com/en/actions/concepts/security/openid-connect)). This avoids duplicating long-lived cloud secrets.
- **OWASP CI/CD:** OWASP’s primary cheat sheet covers secure SCM configuration, pipeline isolation, least privilege, secrets, dependency/plugin management, integrity verification/signing, and monitoring ([OWASP, “CI/CD Security Cheat Sheet”](https://cheatsheetseries.owasp.org/cheatsheets/CI_CD_Security_Cheat_Sheet.html)).
- **OWASP secrets:** central management, encryption, least privilege, rotation, auditing, separation of environments, and avoiding source-code plaintext are recurring primary-source controls ([OWASP, “Secrets Management Cheat Sheet”](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)). Log masking is a defence, not proof that a secret was never exposed.
- **OpenSSF measurement:** Scorecard automates heuristics such as branch protection, code review, dangerous workflows, pinned dependencies, token permissions, and signed releases ([OpenSSF Scorecard](https://github.com/ossf/scorecard)). It is useful feedback and dependency risk evidence, not a certification or substitute for control ownership.
- **Agent-specific threats:** OWASP’s 2026 Agentic Top 10 treats goal hijack, tool misuse/exploitation, identity/privilege abuse, agentic supply-chain vulnerabilities, unexpected code execution, memory poisoning, and cascading failures as distinct risks ([OWASP, “Top 10 for Agentic Applications 2026”](https://genai.owasp.org/download/52117/), especially ASI01 pp. 9–11, ASI02 pp. 12–14, ASI03 pp. 15–17, ASI04 pp. 18–20, and ASI05 pp. 21–23). Its mitigations include treating external content as untrusted, least privilege, human approval for high-impact or goal-changing actions, auditable goal constraints, and monitoring.
- **Host enforcement:** Anthropic states that permission rules are enforced by Claude Code, while prompt/`CLAUDE.md` instructions only shape what the model attempts; its sandbox separately enforces OS-level filesystem and network limits ([Anthropic, “Configure permissions”](https://code.claude.com/docs/en/permissions#manage-permissions), [“Configure the sandboxed Bash tool”](https://code.claude.com/docs/en/sandboxing)). Codex similarly documents an OS-enforced sandbox and approval policy, with network access off by default in its operating model ([OpenAI, “Agent approvals & security”](https://learn.chatgpt.com/docs/agent-approvals-security)).

### Concrete starter controls

| Area | Baseline control | Enforcement/evidence |
|---|---|---|
| Dependencies | Commit the ecosystem lockfile; maintain a dependency manifest; use Dependabot or equivalent for version/security updates; export an SBOM; fail or require explicit risk acceptance for critical/high exploitable findings. | Lockfile diff, alert/review policy, SBOM attached to releases. Do not silently auto-merge risky updates. |
| Actions and build images | Pin third-party actions to full commit SHAs; use immutable digests for build images; record the upstream version beside the SHA for maintainability. | Repository policy/linter plus dependency-update PRs. |
| Workflow identity | Default `GITHUB_TOKEN` to `contents: read`; grant only job-specific permissions. Use OIDC/short-lived cloud identity for deploys. Never expose a broad PAT where a job-scoped identity works. | Workflow syntax/policy check; cloud trust conditions; token-permission audit. |
| Untrusted PRs | Do not check out and execute untrusted PR code in a privileged context with secrets. Avoid `pull_request_target` unless its privilege separation is designed and reviewed; do not expose self-hosted runners to public fork PRs. | Separate unprivileged test workflow from privileged merge/deploy workflow. |
| Secrets | No secrets in source, images, examples, or agent memory. Use the platform/organization secret manager; prefer workload identity; separate environments; rotate and revoke; mask derived values; audit reads. | Secret scanning + push protection, secret-manager audit, rotation test. |
| Source and release integrity | Protected default/release branches, required review, required status checks, immutable release tags, archived release materials/checksums, and build provenance. | Branch rules, release workflow, provenance/SBOM/test evidence. |
| Agent runtime | Ephemeral worktree/container/VM; non-production identity; read-only sensitive paths; workspace-only writes; default-deny or narrow egress; no credential inheritance; no deployment/merge authority. | Host sandbox policy, short-lived identity, network policy, audit log. |
| High-impact actions | Require a human/policy service to validate exact action, target, parameters, scope, and expiry for releases, payments, deletion, privilege changes, external publication, or production writes. | Bind approval to the action; log requester/approver/target/outcome; replay protection. |
| Security reporting | Include `SECURITY.md`, supported-version table, private reporting route, and response ownership. | Test that the route reaches the security owner. |

### Explicit inferences and template decisions

- **[Template decision]** Make the default agent profile read-only or workspace-write with network disabled/allowlisted. Provide separate reviewed profiles for dependency installation, browser testing, and deployment; none is the default.
- **[Template decision]** Treat agent output as an untrusted change proposal: agents may edit a branch and open a PR, but protected-branch merge, secret-bearing workflows, and production deployment remain human-authorized.
- **[Template decision]** Start a portable template with dependency locks, SBOM generation, signed release/provenance workflows, and policy files, but do not print a SLSA badge or level until an independent control review verifies it.
- **[Inference]** Least privilege is defence in depth, not a cure for prompt injection: combine narrow identity, sandboxing, input/tool separation, approval for impactful actions, and monitoring.
- **[Template decision]** Run security tooling in CI but retain human ownership of exceptions. A scanner result is evidence; it is not permission to ignore a true positive.

## 3. Product quality: architecture, testing, observability, accessibility, documentation

### Architecture and quality targets

- ISO/IEC/IEEE 42010 specifies the structure of architecture descriptions for software, systems, products, and other entities; it does **not** prescribe microservices or a particular source-tree layout ([ISO/IEC/IEEE 42010:2022 official catalogue](https://www.iso.org/standard/74393.html)). A template can use it to keep architecture descriptions consistent.
- ISO/IEC 25010:2023 defines nine product-quality characteristics intended to be specified, measured, and evaluated through the lifecycle, including requirements, design objectives, tests, and acceptance criteria ([ISO/IEC 25010:2023 official catalogue](https://www.iso.org/standard/78176.html)). This supports a `QUALITY.md` with measurable acceptance/SLOs rather than “best practices” prose.
- OpenAI’s agent-first report supplies a directly relevant first-party pattern: divide domains into a fixed set of layers, permit only validated dependency directions, and enforce the structure with linters and structural tests ([OpenAI, “Harness engineering”](https://openai.com/index/harness-engineering/)). This supports modular boundaries, but the specific topology below is a template choice.

**Template decision:** start as a **modular monolith by default**, not a microservice mesh. Each business capability owns its public interface, implementation, and tests; cross-module access is explicit; dependency direction is linted. Split a module into a separately deployable service only when scaling, isolation, ownership, or failure boundaries justify the operational cost. This is an engineering choice, not a requirement of ISO 42010 or SLSA.

### Testing and verification

- ISO/IEC/IEEE 29119-1:2022 supplies common software-testing concepts and terminology for the 29119 series ([ISO official catalogue](https://www.iso.org/standard/81291.html)). NIST SSDF Release/Respond practices add security testing and evidence. These sources do **not** mandate a universal test-to-code ratio.
- Convert each ISO 25010-style quality goal into an observable check: contract/unit tests at module boundaries; integration tests against real persistence/protocols; acceptance tests for user journeys; security tests; and smoke/observability checks for release evidence. Keep the exact mix proportional to risk.
- Make `AGENTS.md` commands match CI and contributor commands exactly. For a state change, assert the resulting row/API response/rendered output—not only a return code or mock. This combines ISO’s acceptance-criteria emphasis with Anthropic’s runnable-check guidance.

### Observability

- OpenTelemetry defines a vendor-neutral telemetry approach and common APIs/SDKs/data models; its signals include traces, metrics, and logs ([OpenTelemetry overview](https://opentelemetry.io/docs/what-is-opentelemetry/), [Observability primer](https://opentelemetry.io/docs/concepts/observability-primer/)). Use OTLP or another explicit export contract so the template does not hard-code one backend.
- W3C Trace Context standardizes `traceparent`/`tracestate` for cross-service correlation and explicitly says those fields must not carry personally identifiable or sensitive information ([W3C Trace Context, §§2 and 6](https://www.w3.org/TR/trace-context/#privacy-considerations)).
- Google’s SRE guidance says monitoring supports attention, diagnosis, visualisation, trends, and change comparison; it recommends configuration as code, purposeful metrics, consistent basic coverage, and testing alert logic ([Google SRE Workbook, “Monitoring”](https://sre.google/workbook/monitoring/)). This is operational guidance, not a mandate to adopt Google SRE as an operating model.

**Template decision:** every service exposes structured logs, request/operation traces, and a small purposeful metric set; trace IDs and telemetry fields are classified/redacted; dashboards and alert-routing tests are versioned. Alert on user-impact/SLO symptoms where applicable rather than every internal event.

### Accessibility

- WCAG 2.2 is a W3C Recommendation with testable, technology-independent success criteria across A, AA, and AAA levels ([W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/)). WCAG itself does not make AA universally mandatory.
- W3C WAI says accessibility should be evaluated early and throughout development and that **no tool alone determines conformance**; knowledgeable human evaluation remains necessary ([W3C WAI, “Evaluating Web Accessibility Overview”](https://www.w3.org/WAI/test-evaluate/)).

**Template decision:** target **WCAG 2.2 AA** for web/UI starters unless the product owner documents a different target. Include semantic HTML, keyboard/focus checks, contrast and zoom checks, accessible names, reduced motion, and automated checks in CI; retain manual testing and user testing for critical journeys. A CI scanner result alone is not a conformance claim.

### Documentation

- GitHub recommends a concise README containing what the project does, why it is useful, how to get started/help, and who maintains/contributes ([GitHub, “About the repository README file”](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes)).
- Diátaxis is a primary-source documentation framework, not a government standard. It separates tutorials, how-to guides, reference, and explanation by user need and organises docs around those needs ([Diátaxis](https://diataxis.fr/)).

**Template decision:** use the repository index to route readers; keep tutorials/how-to/reference/explanation distinct; generate API reference from schemas where possible; link-check docs and require doc changes in the same PR as behaviour changes. The “same PR” rule is a project policy, not a Diátaxis mandate.

## 4. Privacy and launch readiness

### Scope before controls

A reusable repository can provide inventory templates, interfaces, retention jobs, consent plumbing, tests, and evidence. It cannot determine the project’s controller/processor roles, lawful bases, notices, jurisdiction-specific ePrivacy rule, sector obligations, or whether its use of data is lawful.

GDPR Article 3’s territorial/material scope includes processing in the context of an EU establishment and, for an establishment outside the EU, offering goods/services to people in the Union or monitoring their behaviour ([GDPR, Article 3](https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng#art_3)). The European Commission’s application page confirms those two branches ([European Commission, “Application of the GDPR”](https://commission.europa.eu/law/law-topic/data-protection/information-business-and-organisations/application-gdpr_en)). The UK GDPR and UK PECR are a separate regime; ICO material must not be silently presented as EU-wide law.

### When each launch-readiness control matters

| Control | Relevant when | Reusable implementation | What the source actually requires/says |

It operationalises accountability without pretending the repository decides legality. |

### What the starter may and may not claim

**May provide (technical starter):**

- `docs/privacy.md` explaining the assessment workflow and owners;
- an Article-30-shaped data-inventory schema, without a preselected lawful basis;
- retention/deletion interfaces and tests;
- a rights-request runbook template and request-routing code;
- a terminal-storage/cookie/SDK inventory and consent-gate adapter interface;
- a DPIA screening questionnaire and decision register;
- vendor/processor/transfer register;
- telemetry classification/redaction rules and automated tests.

**Must not claim without project-specific evidence:**

- “GDPR compliant,” “ICO compliant,” or “privacy by design compliant”;
- that a banner makes all worldwide cookie law satisfied;
- that a ROPA template is the organisation’s complete legal ROPA;
- that a DPIA screening answer equals a DPIA;
- that data minimisation/anonymisation has been achieved without data-flow and re-identification analysis;
- that a technical control resolves a residual legal risk.

## 5. Skills discovery, packaging, and source quality

### Open packaging and discovery

- The Agent Skills specification defines a skill directory with required `SKILL.md` (YAML frontmatter plus Markdown) and optional `scripts/`, `references/`, and `assets/`. Required fields are `name` and `description`; optional fields include `license`, `compatibility`, `metadata`, and experimental `allowed-tools` ([Agent Skills specification](https://agentskills.io/specification)).
- The open-standard implementation guide defines three-tier progressive disclosure: metadata at session start, full instructions on activation, resources on demand. It recommends under 5,000 instruction tokens, keeping `SKILL.md` under 500 lines, and one-level file references ([Agent Skills, “How to add skills support”](https://agentskills.io/client-implementation/adding-skills-support), [specification § Progressive disclosure](https://agentskills.io/specification#progressive-disclosure)).
- The standard’s script guidance says to pin one-off package versions, state prerequisites, use meaningful exit codes, bound output, provide safe defaults/dry runs for destructive work, and test bundled scripts ([Agent Skills, “Using scripts in skills”](https://agentskills.io/skill-creation/using-scripts)).
- GitHub documents project skill locations (`.github/skills`, `.claude/skills`, `.agents/skills`), `gh skill` discovery from GitHub repositories, and points users to `anthropics/skills` and GitHub’s `github/awesome-copilot` as online examples ([GitHub, “About agent skills”](https://docs.github.com/en/copilot/concepts/agents/about-agent-skills)). These are discovery starting points, not blanket endorsements.
- Anthropic’s official skills repository says its entries demonstrate possibilities, identifies open-source versus source-available material, and explicitly asks users to test skills before critical use ([`anthropics/skills` README](https://github.com/anthropics/skills#disclaimer)).
- `skills.sh` is a Vercel-operated directory with “official” publisher listings and third-party audit panels. Its own documentation says rankings are based on anonymous install telemetry and it **cannot guarantee the quality or security of every listed skill** and encourages review before installation ([skills.sh documentation, “How are skills you securing skills?”](https://www.skills.sh/docs#how-are-skills-you-securing-skills), [Security Audits](https://www.skills.sh/audits)). Therefore an “official” label means the technology maker publishes the repo; it is not a security certification.

### Mandatory skill admission process

1. **Identify the canonical publisher and source.** Prefer the vendor’s first-party repository or an explicitly authorised partner. Record owner/repository, canonical URL, licence, release/tag, immutable commit SHA, and why the publisher is authoritative. A directory badge, star count, or install count is not provenance.
2. **Read before install.** Review `SKILL.md` and every referenced script, reference, asset, package manifest, hook, MCP declaration, and binary. Inspect repository history/ownership and search for shell download/execution, credential paths, network endpoints, destructive commands, obfuscation, hidden files, and instructions that conflict with the requested task. Anthropic warns that plugins can execute arbitrary code with user privileges and that marketplace ownership does not establish what each plugin does ([Anthropic, “Plugin security and trust”](https://code.claude.com/docs/en/plugins/security)).
3. **Derive the permission envelope before enabling it.** List required read/write paths, processes, network domains, tools/MCP servers, and secrets. Start with none; grant only the minimum. Treat `allowed-tools` as experimental metadata, not a host-enforced sandbox.
4. **Test in a disposable, unprivileged environment.** Use a throwaway repository/worktree/container/VM with no production credentials, restricted egress, and a test account. Observe file/network/process effects and outputs. Start with fake/canary data. Do not test on a workstation or repository holding secrets.
5. **Pin and record the exact revision.** Vendor or install from an immutable commit/digest, record the SHA and local content hash in a reviewed lock/allowlist, and prohibit mutable `latest`, branch names, or unpinned `npx` execution for admitted skills. Pinning a skill repository and recording who approved it is a **template decision**; the underlying version/script-pinning principles come from the official skill-script and GitHub action guidance.
6. **Review updates as code changes.** Fetch metadata/diff only, identify added instructions/scripts/dependencies/permissions, rerun evaluation and security review, obtain the same approval as the initial admission, and never auto-update an enabled privileged skill. Disable auto-update for production/agent fleets where supported.
7. **Retain an allowlist and revocation path.** Record owner, purpose, version, permissions, evaluation result, review date, and replacement/removal procedure. Revoke immediately when the publisher, source, permission envelope, or behaviour changes unexpectedly.

## Consolidated template decisions and inferences

These are **not direct mandates from the cited sources**:

1. **50–150-line root `AGENTS.md` target.** Chosen to fit OpenAI’s ~100-line example and Anthropic’s under-200-line guidance while leaving room for tooling-specific adapters.
2. **`docs/README.md` as the canonical navigation index.** A concrete response to the sources’ map/system-of-record patterns, not a named GitHub requirement.
3. **No manual duplicate instruction sets.** Generate client-specific files or make them minimal pointers; reject contradictions mechanically. GitHub explicitly recommends avoiding conflicts but does not mandate this generation architecture.
4. **Modular monolith by default.** ISO 42010 documents architecture; it does not select a topology. The starter chooses the lowest-operations boundary that still enforces clear interfaces.
5. **WCAG 2.2 AA as a web starter target.** W3C defines the levels; the project owner must choose and record the target and verify it.
6. **OpenTelemetry as the default telemetry contract.** Vendor-neutral and portable, but the product owner may need a different protocol or backend.
7. **Agent approval boundaries for merge/deploy/high-impact actions.** A conservative synthesis of least-privilege/agentic-risk guidance; exact risk tiers must match the product.
8. **Immutable skill admission record and manual updates.** The standard defines packaging, not an organisation’s admission policy; this is a supply-chain control decision.
9. **Privacy intake, ROPA-shaped inventory, DPIA screening, and legal-review gate.** Technical scaffolds that support accountability; none establishes legal compliance and none replaces counsel.
10. **Cookie reject/accept parity.** Adopted as a conservative UX and UK ICO-aligned default, not asserted as the complete legal rule in every EU Member State or other jurisdiction.

## Verification limits and source-quality notes

- **No unverified third-party skill is recommended.** Anthropic’s official examples, GitHub’s collections, and `skills.sh` are listed only as discovery sources subject to the admission process. No skill package was installed or executed for this research; only public standards, repository READMEs, and documentation were read.
- **Living documentation:** OpenAI, Anthropic, GitHub, OWASP, and `skills.sh` pages can change after the cutoff. Their stable architectural/security principles are used here; version-specific features added after 2026-08-25 should not be backdated into this note.
- **Extractability limits:** direct automated retrieval returned an empty HTTP 202 response for EUR-Lex’s GDPR/ePrivacy pages, and ISO’s full standards are paywalled. Canonical URLs and official catalogue/search excerpts were verified, and legal claims were cross-checked against official European Commission/EDPB/ICO guidance. No cited URL was dead, but the full ISO texts and EUR-Lex extraction were not independently line-inspected in this session.
- **Standards are not certifications:** using an SSDF mapping, SLSA workflow, OpenSSF score, OWASP control, WCAG target, GDPR template, or legal-review artefact does not by itself demonstrate conformance.

## Bottom line

The strongest portable pattern is a **small, navigable instruction surface over versioned repository-local truth**, with **mechanically enforced boundaries and runnable verification**. Security and privacy controls must be capabilities and platform policy—not prose an agent is asked to remember. Skills are valuable portable packages but also untrusted supply-chain inputs until reviewed, permissioned narrowly, tested, and pinned.

## 2026-08-25 follow-up — practical prompt patterns and legal-risk reduction

**Fresh-pass boundary:** This follow-up uses current official or primary sources accessed **2026-08-25**. Direct requirements are separated from **[Template decision]** and **[Inference]**. The prompt patterns below are engineering templates, not legal advice; no template, consent banner, policy, test, provider certificate, or technical control prevents lawsuits, establishes a lawful basis, or guarantees compliance in any jurisdiction.

### A small reliable prompt contract

The portable unit is a short **task contract**, not a copied collection of personas or “mega-prompts.” OpenAI’s current Codex guidance recommends a prompt default of **goal, context, constraints, and “done when”** ([OpenAI, “Best practices – Codex”](https://developers.openai.com/codex/learn/best-practices)). The other fields turn that useful default into an auditable unit of work.

| Element | Put this in the task | Reusable practice and status |
|---|---|---|
| **Objective** | One user-visible or operational outcome plus explicit non-goals. | Prefer “reduce p95 checkout latency below `X` without changing `Y`” over “improve checkout.” OpenAI’s four-part default supports the first half; the non-goal is a **[Template decision]**. |
| **Context** | The exact issue, acceptance owner, source-of-truth files, schemas, current failure/evidence, and what the agent must read before acting. | Link or name relevant context rather than pasting every document. OpenAI reports that a map beats a huge instruction file; Anthropic and GitHub likewise recommend concise, relevant, scoped context ([OpenAI, “Harness engineering”](https://openai.com/index/harness-engineering/); [Anthropic, “How Claude remembers your project”](https://code.claude.com/docs/en/memory); [GitHub, “Prompt engineering for GitHub Copilot Chat”](https://docs.github.com/en/copilot/concepts/prompting/prompt-engineering)). |
| **Constraints** | Allowed files/tools/data, architecture and security invariants, prohibited actions, permissions, and escalation conditions. | State the boundary, but enforce it in the sandbox, IAM, CI, or protected branch. A prompt is not an authorization control. These exact fields are **[Template decision]**, grounded in the vendors’ documented goal/context/constraint model. |
| **Acceptance** | Observable behavior, non-regression conditions, and the test/fixture/artifact that distinguishes pass from partial success. | Put “done when” before implementation. GitHub recommends examples—including tests—and breaking a large task into smaller tasks; OpenAI likewise asks for behavior-changing or no-longer-reproducing evidence ([OpenAI, “Best practices – Codex”](https://developers.openai.com/codex/learn/best-practices); [GitHub, “Prompt engineering for GitHub Copilot Chat”](https://docs.github.com/en/copilot/concepts/prompting/prompt-engineering)). |
| **Evidence** | Exact command or workflow, expected result, and the real artifact/state to inspect: row, API response, rendered screen, log, metric, package, or report. | Verification should inspect the running outcome, not only compilation. OpenAI made worktree apps, UI, logs, metrics, and traces directly legible to the agent; Anthropic recommends a pass/fail verification signal ([OpenAI, “Harness engineering”](https://openai.com/index/harness-engineering/); [Anthropic, “Best practices for Claude Code”](https://code.claude.com/docs/en/best-practices)). |
| **Independent review** | A fresh, read-only review context receives the objective, acceptance criteria, final diff/artifact, and evidence log; it must try to falsify the completion claim before a human accepts it. | Anthropic documents fresh, isolated subagent contexts with separate tool access and permissions. Using that mechanism for an independent review is a **[Template decision]**; treating same-model review as insufficient for human/specialist sign-off is an **[Inference]** ([Anthropic, “Create custom subagents”](https://code.claude.com/docs/en/sub-agents)). |
| **Iteration budget** | Maximum attempts/checks, what changes between attempts, and explicit success, blocked, no-progress, and escalation stop conditions. | OpenAI’s goal pattern includes outcome, verification surface, constraints, boundaries, iteration policy, blocked stop, and budget ([OpenAI, “Follow a goal”](https://developers.openai.com/codex/use-cases/follow-goals)). A starter default of at most three focused evidence-led loops is a **[Template decision]**; each task may declare another bound, and the agent must stop and report rather than loop indefinitely. |

**Repository workflow [Template decision], without a prompt library:**

1. Keep a short root `AGENTS.md` as the map; keep path-specific rules scoped and detailed procedures in one-hop documents. GitHub supports repository-wide, path-specific, and `AGENTS.md` instructions but warns against conflicting sets ([GitHub, “About customizing GitHub Copilot responses”](https://docs.github.com/en/copilot/concepts/prompting/response-customization)).
2. Put the objective, acceptance evidence, risks, and non-goals in the issue or task record; do not turn always-on instructions into a backlog.
3. For material work, use a compact **specification → plan → tasks → implementation → convergence** artifact chain. GitHub’s first-party Spec Kit demonstrates that pattern, but adopting the repository or its skills is optional and was not done for this research ([GitHub, “Spec Kit”](https://github.com/github/spec-kit)).
4. Let the agent inspect the environment and repository truth before editing; expose logs, tests, and the running surface rather than asking it to infer success.
5. Run the exact declared checks, inspect the real artifact, then obtain a fresh review of the diff and evidence. Stop after the declared iteration budget and leave unresolved legal, provider, or product decisions as open gates.
6. Convert recurring failures into repository-local instructions, tests, schemas, or enforcement—not an ever-growing prompt appendix.

### AI-agent supply-chain, prompt-injection, and action-security controls

OWASP’s 2026 Agentic Top 10 treats goal hijack, tool misuse, identity/privilege abuse, agentic supply-chain vulnerabilities, unexpected code execution, memory/context poisoning, insecure inter-agent communication, cascading failures, trust exploitation, and rogue agents as distinct risks ([OWASP, “Top 10 for Agentic Applications 2026”](https://genai.owasp.org/download/52117/)). OpenAI and Anthropic both treat untrusted tool/web/document content as a prompt-injection path; prompt wording alone is not a security boundary. The control profile below is a conservative **[Template decision]** to adapt by risk, not a universal mandate or certification.

| Agent risk | Minimum technical control | Operator evidence |
|---|---|---|
| **Goal hijack and indirect prompt injection** | Label every source and trust level; keep external/user/tool content in a data channel that cannot change policy, goal, tool scope, or approval; use typed schemas/enums for parameters; extract only required fields; never elevate retrieved instructions to developer/system authority. | Direct/indirect injection eval set; webpage/email/document/tool-output fixtures; traces proving tool parameters stayed within the original task; red-team cases and regressions. |
| **Tool misuse, identity, and privilege abuse** | Give each agent/task a short-lived identity and minimum read/write scopes; enforce filesystem, network, resource, and secret boundaries outside the model; authorize every call server-side; use separate tools/identities for untrusted users and sensitive systems. | Policy tests for denied paths/scopes; cross-tenant and confused-deputy tests; secret-use audit; approval records; incident drill. Prompt text such as “never delete” is supplementary only. |
| **Agentic software/model supply chain** | Inventory and pin base/fine-tuned models, adapters, datasets where applicable, prompts/instruction files, tools/plugins/MCP servers, packages, containers, and runtimes; verify hashes/signatures and provenance; scan before admission; isolate; review permission/schema/code diffs on updates; record SBOM/AIBOM evidence. Treat mutable `latest`, unsigned remote scripts, and unreviewed skills/MCP servers as untrusted. | Admission record with publisher/revision/digest/permissions; reproducible build or artifact digest; vulnerability/unsafe-serialization results; update-review diff; rollback/revocation test. Exact inventory fields are a **[Template decision]** implementing NIST’s secure AI acquisition/development profile and OWASP ASI04. |
| **Memory and context poisoning** | Do not automatically persist raw external/user content as instructions. Classify fields; record provenance and tenant; allowlist writable memory types; validate/quote retrieved data; isolate sessions/users; set size/expiry; protect integrity; support correction and deletion. | Memory-write audit, expiry/cross-tenant tests, source/provenance samples, poisoned-RAG cases, and deletion propagation. |
| **Improper output/code/tool-result handling** | Treat model output and tool results as untrusted. Validate against a schema; parameterize database/shell/API operations; never interpolate into code or privileged URLs; contextually encode output; sandbox execution; block secret access and unsafe deserialization; verify side effects after the call. | Malicious Markdown/HTML, command, path, SQL, URL, serialized-object, and tool-result fixtures; authorization and side-effect assertions; sandbox escape attempt. |
| **Cascading failures and denial of wallet** | Enforce maximum steps, tool calls, recursion/inter-agent depth, wall time, tokens/cost, and output size; use idempotency keys, circuit breakers, cancellation, deadlines, budgets, and a human kill switch. High-impact calls require exact-action approval. | Budget-exhaustion and retry-storm tests; cancellation/rollback drill; rate and spend alerts; exact target/parameter/expiry binding; no silent retry of irreversible actions. Limits and budgets are **[Template decisions]**. |
| **Independent review and audit** | Give a fresh, read-only reviewer the objective, acceptance criteria, diff/artifact, evidence, and threat model. Log prompt/instruction/model/tool version, source, tool call, normalized arguments, approver, result, and error with least-privilege access, redaction, integrity protection, and retention. | Reviewer report with blockers, eval output, sampled traces, access audit, and resolved/false-positive reasoning. Human review and specialist review remain separate from another model’s opinion. |

**Filter boundary:** structured prompts, classifiers, sanitizers, and model guardrails can reduce exposure, but OpenAI says structured outputs and isolation do not fully remove arbitrary-text risk, while Anthropic recommends layering input screening, untrusted-content handling, output screening, least privilege, monitoring, and red-teaming ([OpenAI, “Safety in building agents”](https://developers.openai.com/api/docs/guides/agent-builder-safety); [Anthropic, “Mitigate jailbreaks and prompt injections”](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks); [OWASP, “AI Agent Security”](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html); [OWASP, “LLM Prompt Injection Prevention”](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)). Do not claim “prompt-injection safe.”

### Reusable prompt patterns — templates, not legal advice

Replace every bracketed placeholder; remove fields that do not apply. The numeric budgets below are examples to set per task, not universal defaults.

**Pattern 1 — implementation task contract**

```text
Objective: Deliver [one observable outcome] for [user/system].
Non-goals: Do not change [protected scope/behavior].
Context: Read [issue/spec], [source-of-truth files], [current evidence], and [architecture/security rules].
Constraints: Use [allowed tools/paths/data]; follow [invariants]; do not [prohibited actions].
Acceptance: [User-visible behavior] AND [non-regression condition].
Evidence: Run [commands/workflow]; inspect [row/API/UI/log/package/artifact] and expect [result].
Independent review: Give a fresh read-only reviewer [objective, acceptance, diff, evidence] before acceptance.
Iteration budget: At most [N] evidence-led attempts; change one falsifiable hypothesis each time.
Stop: Continue only if [progress condition]; otherwise stop and report [blocker, evidence, next decision needed].
```

**Pattern 2 — current primary-source research**

```text
Objective: Answer [question] from current official/primary sources only.
Context: Scope [jurisdictions/products/date cutoff]; read [local source of truth] first.
Constraints: For every claim, capture claim-level URL, publisher, exact title, access date, and concrete reusable practice. Distinguish [Source requirement] from [Inference] and [Template decision]. Do not use a secondary summary when the owner publishes the source.
Acceptance: All requested topics covered; important conflicts or uncertainty visible; no unsupported “compliant”/“safe” claim.
Evidence: URL reachability/canonical-source check plus claim-to-source audit.
Independent review: Fresh reviewer tries to trace each consequential claim to the cited owner.
Iteration budget: [N] focused passes; stop when new searches no longer change a material claim.
Output: Concise synthesis, source register, unresolved questions, and exact artifact changed.
```

**Pattern 3 — privacy and website launch assessment**

```text
Objective: Produce a factual launch-risk assessment, not legal advice or a compliance certificate.
Context: Operator [identity/form/address]; jurisdictions [countries]; audiences [including minors]; data flows [fields/stores/providers/transfers]; contracts [terms/subscription]; runtime [cookies/SDKs/marketing/accessibility].
Constraints: Separate EU GDPR, national ePrivacy implementation, UK rules, German obligations, and US rules. Do not invent a lawful basis, age threshold, retention period, transfer mechanism, operator fact, or approval.
Check: Scope/accountability; by-design/defaults; records; retention/deletion; rights; cookies; minors; marketing; terms; Impressum; accessibility; agent/security risks.
Acceptance: Each topic has current primary sources, factual control, missing fact, owner, and evidence state.
Evidence: Link/capture/inventory output, request/deletion tests, rendered-page review, and versioned inventory.
Gates: Flag counsel, DPO, DPIA, provider, accessibility-specialist, and unresolved high-risk items separately.
Close: [implemented/verified/pending/blocked] with owner/date; no “compliant” claim without project-specific evidence.
```

**Pattern 4 — agent/tool security design**

```text
Objective: Design/review [agent workflow] without treating prompt text as a security boundary.
Context: Agents [roles]; tools/MCP [inventories]; identities/scopes [current]; data [classes]; external inputs [web/issues/docs/MCP]; model/prompt/dependency provenance [digests].
Constraints: Untrusted content cannot set goals or permissions. Minimize tools/data/secrets; validate every input, output, and side effect; require exact-action approval for [high-impact actions].
Acceptance: Threat model covers goal hijack, tool/identity misuse, supply chain, memory poisoning, code execution, cross-agent trust, cascading failure, and denial of wallet.
Evidence: Permission/config tests, SBOM/AIBOM/admission records, injection/poisoning eval results, sandbox and side-effect tests, budget/kill-switch drill, audit samples.
Independent review: Fresh read-only security reviewer attempts privilege escalation, exfiltration, indirect injection, and cross-tenant cases.
Iteration budget: [N] remediation/retest loops; stop and escalate on residual high risk.
Output: Control-to-evidence map, residual risk, owner, expiry, and re-test trigger.
```

**Pattern 5 — independent completion review**

```text
Objective: Try to falsify the claim that [change/research] satisfies [original acceptance criteria].
Inputs: Original request/spec, final diff/artifact, command outputs, runtime observation, source/citation inventory, known residual risks.
Constraints: Read-only; do not silently repair. Do not treat the builder’s explanation, a green build, a scan, or another model’s confidence as proof.
Review: Re-run the smallest critical checks; trace material claims to artifacts/sources; probe security/privacy/licensing/accessibility regressions and missing evidence.
Acceptance: Report confirmed blockers separately from questions/inferences; cite exact file/line, URL, command output, or observed state for every finding.
Output: `blockers | residual risks | evidence gaps | verdict` with a concrete next action and owner.
```

### Launch-risk matrix: keep the evidence classes separate

A **technical control** is implemented in code/config/policy. **Operator evidence** proves the deployed or local artifact behaved as intended. **Counsel evidence** is a qualified legal conclusion about stated facts/jurisdictions. **Provider evidence** is a provider contract, technical attestation, or service-specific commitment. A provider document is not legal advice; counsel approval is not a substitute for a test; neither substitutes for the other. Keep the matrix with launch evidence and mark an unresolved applicable cell as `pending` or `blocked`.

| Launch risk | Technical controls | Operator evidence | Counsel evidence | Provider evidence |
