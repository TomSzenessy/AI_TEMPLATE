# One capability model

<!-- index: extend | The capability model: kinds, declaration fields, discovery, packs, and what is out of scope | You add, find, or switch off a skill, role, doc, rule, check, command, MCP route, or pack. -->

Issue #14. This record is the plan; work that is not listed here is out of
scope until a new issue changes it.

## Context

Skills, roles, and docs could be created with `make new` and found with
`make where`, but every other extension point needed a hand edit to a central
kit file: checks lived in `garden.py` and `structure.py`, 33 commands in
`repoctl.py` plus hand-written Makefile recipes, MCP routes in
`resources.toml`, and always-on rules in `AGENTS.md`. Each kind also had its own
metadata format. A project that edits kit files conflicts with
`make kit-update`, so every hand-registered extension was a future merge
conflict, and a template bug copied into many projects.

## Decision

**One record for every capability.** Every capability is a file that declares
the same core fields, parsed by one loader (`tools/kit/registry.py`):

| Field | Meaning |
|---|---|
| `name` | kebab-case, unique within its kind |
| `description` | `<what it does>; <when to use it>` |
| `pack` | the pack it belongs to; omitted means `core` (always on) |

Kind-specific fields stay with their kind:

| Kind | Lives in | Carrier | Extra fields |
|---|---|---|---|
| skill | `.agents/skills/<name>/SKILL.md` | frontmatter | — |
| agent (role) | `.agents/agents/<name>.md` | frontmatter | `access`, `tier` |
| rule | `.agents/rules/<name>.md` | frontmatter | `scope` (globs; none means global) |
| pack | `.agents/packs/<name>.md` | frontmatter | `default` (on or off) |
| mcp | `.agents/mcp/<name>.toml` | TOML | `transport`, `command` or `url`, `env_headers`, `enabled` |
| check | `tools/kit/checks.py`, `.agents/checks/*.py` | `@check(...)` | `blocks`, `reason` |
| command | `tools/kit/commands.py`, `.agents/commands/*.py` | `@command(...)` | arguments with their make variable |
| doc | `docs/**/*.md` | `<!-- index: -->` comment | `group`, `covers` |

Docs keep their one-line HTML comment because people read docs on GitHub,
where frontmatter would render as a table; the loader maps it to the same
record. The carrier differs only by file type; the fields and the loader do not.

**Discovered, never registered.** Adding a file adds the capability. Nothing
is listed by hand in `project.toml`, `repoctl.py`, the Makefile, or
`AGENTS.md`. Derived views (host adapters, the Makefile command block, the
docs index, the role table, the global rules block in `AGENTS.md`) are
regenerated by `make sync` and checked for drift, as before.

**Kit and project stay apart.** Kit capabilities live in `tools/kit/` and the
kit's `.agents/` files; a project's own capabilities are new files in
`.agents/`. `make kit-update` replaces only files it shipped, so a project's
checks, commands, rules, and routes never conflict with a template fix.

**Checks declare whether they block.** `@check(blocks=True, reason=...)`: a
blocking check must name its evidence (the blocking rule in
`docs/self-healing.md`) or loading fails. Every check returns findings that
name their fix. `make check` and the gates run the blocking checks of enabled
packs; `make garden` runs all of them.

**Commands register themselves.** `@command` declares the help line, the
group shown by `make help`, and each argument's make variable. The Makefile's
command block and `make help` are generated from those declarations, so a
project command in `.agents/commands/` becomes `make <name>` after `make sync`.

**Packs switch groups off without deleting them.** `project.toml`
`[packs] enabled = [...]` overrides each pack's `default`. A disabled pack's
skills and roles are not rendered into host adapters, its rules are not
rendered, its checks do not run, and its commands refuse with the line that
enables them. It still appears in `make capabilities`, `make where`, and
`make similar`, so it can be found. The kit ships two packs: `product` (build
a product: kickoff, stack, UX, research, `make next`, `make ui-review`; on) and
`measure` (`make eval`, `make trial`; off in new projects, on in the template).
Launch evidence stays in the core: it already switches on by `phase`, and a
pack that only hides `make readiness` would save nothing. A third-party
skill's files are pinned by digest, so its pack is recorded in its `[[skills]]`
provenance entry instead of its frontmatter.

**Rules reach the agent when they apply.** A global rule is one line in a
generated block of `AGENTS.md`. A scoped rule is delivered by the after-edit
hook the first time a matching path is edited in a session, and by
`make where`, so rules can grow without growing the router.

**One path to add or find anything.** `make similar Q="<need>"` searches every
kind, including disabled packs. Nothing similar: the `skill-scout` role searches
registries and the web and vets the result ([`../skills.md`](../skills.md)),
and `make new KIND=<kind>` writes the stub with valid metadata, wires it in,
and leaves `FILL-IN:` lines that fail until the content is real.

**Real redundancy merges in the same change:** one reviewer and date rule for
issues and CI (`core.reviewer_problem`); one headless-agent launcher shared by
`make eval` and `make trial` (`evals.run_headless`); one metadata loader for
every kind. `make init`, `make adopt`, and `make kit-update` already share their
install steps (initialization, the lock, Markdown localization, and now target
renaming for the generated Makefile block); what remains different between them
is behavior (adopt merges collisions, an update compares hashes), so they stay
separate commands. A near-duplicate is refused only within its own kind, so a
new MCP route is never blocked by a similarly named command.

## Out of scope

No new end-user features: no new product skills, no telemetry, no new
registries, no change to the issue contract, gate semantics, or governance
profiles. Commands keep their names and arguments.

## Consequences

`repoctl.py` shrinks to discovery and dispatch; `garden.py` keeps only the
report. Existing projects pick the change up with `make kit-update`. A project
that wrote its own Makefile targets keeps them in `project.mk`. Because
`[[mcp]]` routes move out of `resources.toml` before the first tagged release,
there is no compatibility reader for the old location.
